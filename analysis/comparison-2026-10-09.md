# 两份解释型 Skill 的深度比较

日期：2026-10-09。对象是本项目保存的两个 SKILL.md 快照；该次比较没有修改它们。随后 v3 升级将原始 v2 移至 `archive/explain-for-understanding-v2-SKILL.md`，本文的 v2 链接已指向该保留副本。

## 结论与适用边界

用户所指的 Karpathy 原话尚待确认。先采用参考项目 README 明确引用的方向：随着 LLM 承担更多工作，人理解其产出成为瓶颈，图和网页可以降低吸收成本。

按这个方向，不能简单判定 v2 全面胜出：

- **让人快速看懂大量 agent 工作、形成反馈：answer-me-with-html 的流程更直接、更完整。** 它定义内容草稿、关系图、真实代码引用、渲染诊断和按面板反馈。
- **让人理解复杂技术机制、知道结论成立的边界：explain-for-understanding v2 的指令更明确。** 它要求事实模型、教学路径、决定性示例、反例及不确定性说明。
- **对于本次 AGC/TPC 场景，优先采用 v2 的解释方法；工程交付值得借用参考项目的渲染与反馈机制。** 这是对指令设计的判断，还不是实测的学习效果排名。

Karpathy 本人在其网站保存的 2022-04-16 推文中强调逐步增加系统模型复杂度、检查变量极限行为和追求简单有力的解法。这支持把“能否形成并运用模型”作为另一项比较标准，但不能替代用户可能指的最新推文。

## 比较口径

区分三个不同层次：

1. 指令要求模型做什么：可以直接检查两份文件。
2. 渲染工具实现并保证什么：须检查或运行配套代码，不能只靠 SKILL.md 宣称。
3. 用户读完是否理解：须用真实阅读任务验证，不能靠模型给自己打分。

本次完成第 1 层并检查本地配套文件是否存在；没有运行两套渲染流程，也没有进行读者实验。原对话的 HTML 评分不是本次的评测数据。

## 机制比较

| 维度 | explain-for-understanding v2 | answer-me-with-html | 判断 |
|---|---|---|---|
| 主要目标 | 形成正确、可检验、能复用的心智模型 | 将回答变成易读页面，并接收用户反馈 | 深度理解与日常协作分别占优 |
| 解释路径 | 因果机制、瓶颈、示例、反例、决策规则 | 按子问题分面板，按信息关系选图 | v2 对推导过程约束更强 |
| 证据语义 | 事实、假设、推导、上界、目标、保证分开 | 禁止编造数据，示意数据标注，可直接引用源代码 | 两者都有保真机制；v2 更关心结论强度 |
| 图形选择 | 先建立可记忆的模型，再挂接细节 | flow、sequence、tree、er 等组件选择表 | 二者都有实质解释设计，不能把参考版称为纯装饰 |
| 交互 | 参数改变应揭示关系，结果须说明测了什么 | 选择、评论、Reply、按面板修订 | 前者偏模型探索，后者偏人机反馈 |
| 阅读深度 | 30 秒、3 分钟、审计三个层次 | sheet 和 doc 两种模板；可按面板定位 | v2 有更明确的逐层阅读目标 |
| 生成实现 | 通常让模型创建独立 HTML；未规定统一渲染器 | Markdown 交给 CLI，CLI 负责布局与图形 | 参考版提供更清晰的内容与渲染分工 |
| 完成检查 | 模型自审 truth / understanding / visual / interaction | CLI 诊断、写作检查、修正重试 | 两者检查的错误类型不同，均不等于读者理解验证 |
| 已有文件更新 | 缺少专门的增量更新约定 | 按 panel patch，保留页面中的草稿 | 参考版更适合持续迭代页面 |
| 当前本地可执行性 | 已有完整指令；产物质量仍须实际验证 | 只有 SKILL.md，缺 scripts/am.mjs 和 references | 当前不能直接复现参考版完整工作流 |

## v2 的实质优势

它降低了一类关键风险：读者正确记住数字，却误解数字支持的结论。例如，需求小于某窗口的容量，只能说明这一检查通过；任务释放时刻、抢占限制和其他窗口仍可能使 deadline 失败。v2 明确要求保留这种区别。

它也要求把图用于建立因果模型：先理解数值在模型中的位置，再展开计算；参数控件用于检验关系。这比仅把原答案分成若干面板，更可能帮助读者将结论迁移到新情境。

最后，30 秒／3 分钟／审计三个深度允许不同背景的读者选择成本。这个设计方向值得保留，但需要实际产物证明三个深度确实能分别读完，而非只有三个标题。

## v2 应优先修正的问题

### 1. 示例再次放大了结论强度

第 8 节只给出 55.71u 的容量与 54u 的需求，却称为 “mathematically feasible”，并直接判断工程余量太小（本地文件第 295 行）。前者缺少可调度证明，后者缺少开销预算或接受阈值。

更准确的表达应是：该窗口的聚合容量检查通过，剩余 1.71u；可调度性和余量是否足够，仍取决于任务时序与开销预算。

### 2. 通用解释方法混入太多特定调度场景规则

该 skill 的 description 覆盖技术、科学、战略与研究，但通用正文反复出现 GM、GE、TPC、S11–S13、4/6/8 和调度策略。第 6 节还将专门的 slack 规则扩展为多个宽泛领域的必选要求。

这会增加跨领域误用的风险。应把具体调度语义和数值放进按需读取的实时系统参考文件，通用正文保留“不要把总量界限升级为系统保证”等可迁移原则。

### 3. 读者模型缺少具体操作

第 16 节要求压缩读者已经接受的内容，但没有明确如何识别读者已有知识、当前疑问和要完成的决定。固定从误区开场、始终给反例，可能在读者只是需要定位一处代码变更时增加负担。

应先识别用户任务：查事实、理解机制、审核变更、做决定或学习迁移；有真实误区时才用反例，不凭空制造一个要纠正的读者观点。

### 4. 完成标准没有落实为验证

第 22 节提出“读者能独立重建推理”，但第 19 节主要是模型检查自己是否写了示例、反例和规则。它不能观察读者是否会用。

重要教学任务可用一个短的预测或迁移题：先让读者判断改变条件后的结果，再展示原因。日常简答则无需强制测验。

### 5. 页面结构有过度固定风险

第 2 节允许省略十步骨架中的不必要步骤，第 12 节却要求 6–10 个部分，第 20 节又默认加入示例、反例及多层结论。它们可能把“小问题”膨胀成长页面。

此外，第 11 节只允许用于测试模型的交互，范围过窄：证据展开、定位、评论和决策反馈即使不改变计算模型，也可能显著降低理解成本。

### 6. slack 定义还需补充分析范围

第 238 行将其定义为不使任何“earlier hard deadline”失败的可重分配计算时间，但 earlier 的参照与覆盖区间不明。更稳妥的要求是：在明确的任务、释放和执行成本模型下，重分配后仍满足分析范围内所有受影响的硬时限约束。仅仅发生在某个 deadline 之前的 idle，并不自动构成可安全利用的 slack。

## 参考版的优势和边界

它对“形成一个可读且可修改的结果”规定得更完整：内容草稿与布局分工、组件选择、真实代码引用、渲染错误定位、用户按面板反馈、局部修订。其 sheet 是默认模板，但也明确提供 doc 线性阅读模板，因此不能断言它只能做平铺仪表板。

需要保留三个边界：

- 渲染通过和写作检查通过，不证明事实正确、因果关系成立或读者理解。
- 页面的 ask 是决策反馈，不自动构成知识掌握测试；“用户接受建议”与“用户理解代价”不同。
- 主动生成页面与 always-on 机制会增加产物和阅读切换。是否值得应取决于人的任务成本，而非生成页面本身是否便宜。

参考版并未系统要求证据强度分类、关键假设、反例或迁移验证。对高要求技术解释，不能仅依赖模型默认能力补齐这些内容。

这里评价的是工作流设计。当前本地缺少 CLI 和引用文件，未验证其布局、移动端显示、视频或校验器实际表现。项目 README 的性能数字是作者报告，不能直接用于证明它比本地 v2 更快或更有效。

## 针对本次 AGC/TPC 的具体判断

要解释“为什么平均利用率约 63% 仍可能接近 deadline 瓶颈”，v2 的机制更合适：建时间模型、明确需求窗口、区分容量与可调度、给出反例，最后形成设计规则。

要让已经理解背景的团队审核“这次改变了哪些 IRQ、时间线和配置”，参考版的代码引用、关系图和按面板反馈更直接。此时重新铺开教学骨架可能拖慢审核。

这两个判断都是从指令推导的预期行为，并未通过重新生成两份 HTML 实测。

## 后续优化方案（本次未实施）

推荐三层职责：

```text
输入材料 + 读者任务
          ↓
解释设计：证据、因果模型、必要示例、结论边界
          ↓
表达方式：简短文本 / 表格 / 静态图 / 可交互模型 / 视频
          ↓
实现与验证：适配渲染器、核对来源与数值、检查显示、收集反馈
```

v2 适合负责第一层；参考版可承担其中若干表达与实现路径。不要把两份文件直接拼接：手写 HTML 与 CLI、固定段落数与面板数、参数交互与反馈交互都需要明确的适用条件。官方 CLI 是否足够承载 v2 的参数探索控件，需要另行检查，不能假定直接兼容。

优先顺序：修正第 295 行的示例结论 → 抽离实时系统专用规则 → 增加读者任务分流 → 选择表达和渲染方式 → 为重要解释加入轻量理解验证。

## 怎样证实哪一个更好

若要实测，用相同模型、推理配置、原始材料和问题，覆盖至少三种任务：理解陌生机制、审核熟悉系统的变更、把规则用于新条件。两份产物匿名展示，交替阅读顺序，避免先读版本教会了后读版本的内容。

记录以下可观察结果，不用模型的主观美观分替代：

- 关键事实与结论边界是否正确。
- 找到关键答案并作出正确决定所需时间。
- 能否说明机制，而非只复述数字。
- 能否正确预测一个未展示的条件变化。
- 是否产生高自信的错误理解。
- 生成等待、修复和来回澄清的总成本。

这是建议的评测方案，本次未执行。
